# Submission protocol

## Public development evaluation

Run the complete public development manifest using an immutable model revision:

```bash
.venv/bin/sanctionbench run \
  --config configs/campaign.example.yaml \
  --max-provider-requests 2916 \
  --max-provider-input-bytes 2108017008 \
  --max-courtlistener-requests 12528
```

The current complete protocol plans 324 successful responses per model:

- 152 citation items in closed-book and tool-assisted conditions: 304 calls; and
- 10 constructed document scenarios in both conditions: 20 calls.

The 18 memorization probes are published as an auxiliary dataset but are not yet part of the runner or the 324-call leaderboard protocol. They must not be included informally in a submitted total. Actual provider request attempts are durably counted before invocation. Retries increase the submission's `model_query_count`, so cost and query reporting do not assume that every logical item succeeded on its first request. The complete three-provider example plans 972 logical live calls. The runner requires explicit approval of the three-attempt ceiling (`972 * 3 = 2,916`) before creating any live client and caps each item at three attempts across resumes. It independently approves the retry-inclusive provider input-byte plan and the conservative CourtListener wire-attempt plan. SDK-managed model retries are disabled, and each CourtListener wire attempt is durably counted before transport.

For the organic track, each repetition contains exactly one isolated successful response per document under the same neutral prompt contract. Planned successful responses are `documents * providers * conditions * repetitions`. Package a one-model organic result index the same way; repeated runs are retained in the bundle and the static leaderboard averages each organic scorecard field across repetitions.

If the organic dataset contains `private_evaluation_only` documents or `provisional_model_assisted` records, the result index and bundle are stamped `provisional_private_evaluation` and `publishable=false`. The public leaderboard rejects such a bundle. This lets organizers validate aggregate packaging locally without turning provisional private results into a release claim.

Packaging fails closed: release status, release tiers, and redistribution statuses are mandatory, and organic metadata is recomputed from the exact hash-verified dataset referenced by the result index. Dropping or relabeling only an aggregate status cannot make a private result publishable.

Package only aggregate results and reproducibility hashes:

```bash
.venv/bin/sanctionbench package-submission \
  --results results/runs/index.json \
  --submitter "Name" \
  --organization "Organization" \
  --model-revision "immutable-provider-version" \
  --endpoint-type hosted_api

.venv/bin/sanctionbench validate-submission \
  --submission leaderboard/submissions/<submission-id>.json
```

The bundle contains no prompts from a private test, raw predictions, credentials, or reasoning traces. It retains the exact tool-evidence snapshot hash for each tool-assisted run so the organizer can bind aggregate metrics to the evidence actually supplied, plus the CourtListener request-ledger hash that accounts for actual wire attempts. Development bundles are `self_reported`; mock bundles are `development_mock`. Neither is an official leaderboard result.

## Official private evaluation

Official submissions are organizer-run. The submitter provides:

- legal entity or research organization;
- exact model name and immutable revision/date;
- hosted API or open-weight execution mode;
- context window and supported structured-output behavior;
- sampling/reasoning settings that cannot be controlled by the evaluator;
- data-retention and training-use terms for submitted court documents; and
- a public model card or technical report where available.

Never place an API credential in an issue, pull request, result bundle, email thread without an approved secure channel, or repository secret controlled by a submitter. The organizer records the credential only in the evaluation secret store and destroys or revokes it after the run.

The organizer runs exactly one successful response per manifest item and condition. Retries are allowed only for transport, rate-limit, or schema failures and are recorded. Tool-assisted evidence is generated by the organizer, checkpointed before dispatch, and injected uniformly; models do not choose their own retrieval stack. Official output publishes aggregate metrics, run identities, tool-evidence hashes, query counts, and error counts, while item-level private failures remain hidden until the holdout retires.

## Leaderboard metrics

Every result displays, separately by task and condition:

- SanctionScore, defined as hallucination recall;
- fake-authority recall and authority-level false-positive rate;
- recall at 1% and 5% FPR and calibration metrics in the detailed artifact;
- DocumentSanctionScore;
- Clean-Audit Rate, requiring zero missed hallucinations in a document;
- extra verifications per document;
- the percentage of documents with zero false accusations; and
- false accusations per 100 real authorities.

Organic results additionally display diagnosis accuracy on caught authorities, page accuracy on caught authorities, and clean-control false-alarm rate. They intentionally leave the conventional authority-level false-positive-rate field empty: open-ended unmatched findings are review workload, not predictions over a fixed supplied inventory.

The public development set has only 55 unique real distractor authorities. Recall at 1% FPR is therefore a diagnostic, not a statistically stable headline claim. An official private release should contain at least 500 independently verified unique real authorities and publish uncertainty intervals.

## Pull-request and portal rules

The generated GitHub issue form collects metadata and never secrets. A pull request may add one validated aggregate bundle under `leaderboard/submissions/`. CI rebuilds the JSON, Markdown, and HTML leaderboards and rejects inconsistent generated output. The public submission schema fixes `official=false` and permits only `development_mock` or `self_reported`; editing a bundle cannot create an official result. Organizer-attested private-holdout results will use a separately signed official-result schema when that holdout is ready.
